# راهنمای اجرای پایلوت — از رفع انسداد تا اولین چرخهٔ مالی واقعی

> این سند برای **شما** نوشته شده، نه برای Claude. هر گام یک دستور دقیق دارد و
> می‌گوید چه چیزی باید ببینید. اگر چیزی آن‌طور که نوشته شده نبود، **همان‌جا
> توقف کنید** و قبل از گام بعد بپرسید — به‌خصوص در بخش مالی.
>
> قاعدهٔ طلایی: **هیچ عمل مخربی بدون بکاپ verify‌شده.**

---

## پیش از هر چیز — چرا این فاز فرق دارد

سیستم ۸۷۷ تست، ۱۴ سوئیت رگرسیون و ۷۸ ماژول سالم دارد؛ ولی **هیچ سازمان واقعی
با آن کار نکرده**. درس تکرارشوندهٔ این پروژه این بوده که باگ‌های واقعی را نه
تست‌ها پیدا کردند و نه build سبز — بلکه **باز کردن صفحه توسط یک کاربر واقعی**.

نمونهٔ همین فاز: اسکریپت سلامت‌سنجی تازه‌ساخته، به‌محض اولین اجرا سه صفحهٔ
عمومی را پیدا کرد که با قطع لحظه‌ای دیتابیس **۵۰۰ می‌دادند** — و ابزار
کانبان معلوم شد اصلاً هرگز ذخیره نمی‌کرده (جزئیات در گزارش فاز).

پس: **انتظار داشته باشید پایلوت باگ پیدا کند. این هدف است، نه شکست.**

## گام ۰ — رفع انسداد دیتابیس 🔴

هفت فاز کار (۲۶.۲۷ تا ۲۶.۳۳) روی سرور نرفته چون رمز PostgreSQL بین دیتابیس و
`.env.local` هم‌گام نیست.

### ۰.۱ بکاپ کامل (اجباری)

```bash
sudo -u postgres pg_dump -d habibazar -F c \
  -f /var/backups/pre-golive-$(date +%Y%m%d-%H%M).dump
ls -lh /var/backups/pre-golive-*.dump
```
**باید ببینید:** فایلی با حجم غیرصفر. اگر خطا داد، جلوتر نروید.

### ۰.۲ تشخیص (بدون تغییر)

```bash
cd /var/www/Website && git pull
sudo bash deploy/fix-db-password.sh --check
```
- خروجی «اتصال فعلی سالم است» → مشکل رمز ندارید، به گام ۰.۴ بروید.
- خروجی «رمز هم‌گام نیست» → ادامه.

### ۰.۳ رفع

```bash
sudo bash deploy/fix-db-password.sh --generate   # رمز امن می‌سازد
# یا اگر رمز خودتان را دارید:
sudo bash deploy/fix-db-password.sh
```

اسکریپت این کارها را می‌کند: بکاپ `.env.local` → `ALTER USER` در PostgreSQL →
نوشتن `DATABASE_URL` → تست اتصال → ری‌استارت PM2 با `--update-env`.

> **نکته‌ای که این انسداد را ساخت:** رمزی که `@` یا `:` یا `/` دارد باید در
> `DATABASE_URL` به‌صورت percent-encoded باشد (`@` → `%40`). اسکریپت خودش این
> کار را می‌کند؛ اگر دستی رمز می‌گذارید، حتماً حواستان باشد.

🔴 اگر `--generate` زدید، **رمز چاپ‌شده را همان لحظه در جای امن ذخیره کنید** —
دوباره نمایش داده نمی‌شود.

### ۰.۴ آوردن هفت فاز کار

```bash
sudo bash deploy/update.sh
```
**باید ببینید:** بدون خطا تمام شود. اسکریپت transcript کامل را در
`/var/log/habibazar-update-*.log` می‌گذارد؛ اگر متوقف شد، مرحله/خط/دستور/کد را
چاپ می‌کند — همان را بفرستید.

## گام ۱ — سلامت‌سنجی 🔴 قبل از هر دادهٔ واقعی

```bash
sudo bash deploy/post-deploy-check.sh
```

این اسکریپت **هیچ چیزی را تغییر نمی‌دهد**؛ فقط می‌سنجد و برای هر بررسی عدد
واقعی چاپ می‌کند.

| بخش | چه چیزی را اثبات می‌کند |
|---|---|
| جدول‌ها ≥۱۴۱ + جدول‌های کلیدی | هفت فاز واقعاً روی سرور آمده |
| `health?probe=deep` | دیتابیس، migration، دیسک، حافظه |
| تراز آزمایشی **و مانده‌های کلیدی** | فقط «متوازن بودن» کافی نیست — مانده بانک/AR/موجودی هم سنجیده می‌شود |
| کلاس BUG-020 | سند برگشت‌خوردهٔ `void`شده وجود ندارد |
| شماره‌گذاری | شمارهٔ سند تکراری صفر |
| RBAC | super_admin فعال، کلید یتیم صفر |
| صفحات فارسی/انگلیسی | هر صفحه در هر دو زبان ۲۰۰ |
| وب‌هوک‌ها | تلگرام/واتساپ/زرین‌پال از بیرون باز |
| بکاپ | بکاپ در ۴۸ ساعت اخیر وجود دارد |

**تا وقتی «ناموفق» صفر نشده، دادهٔ واقعی وارد نکنید.**

اگر کلاس BUG-020 خطا داد:
```bash
cd /var/www/habibazar
npx tsx deploy/fix-bug020-data.ts --dry-run    # اول فقط گزارش
npx tsx deploy/fix-bug020-data.ts --confirm    # بعد از بررسی خروجی
```

## گام ۲ — کلیدهای واقعی

همه در `/admin/settings/integrations`. کلیدها **write-only** ذخیره می‌شوند:
بعد از ثبت فقط یک نشانهٔ ماسک‌شده (`•••• 1234`) می‌بینید، خودِ کلید هرگز
برگردانده نمی‌شود.

| سرویس | چه چیزی لازم است | تست واقعی (نه sandbox) |
|---|---|---|
| **مودیان** | کلید خصوصی + شناسهٔ حافظهٔ مالیاتی | یک صورتحساب نمونه → ارسال → تأیید سازمان |
| **زرین‌پال** | merchant id تولید | پرداخت واقعی ۱۰٬۰۰۰ ریال → callback → ثبت در `sales_payments` → پست GL → **استرداد همان مبلغ** |
| **پیامک** | کلید API + شمارهٔ خط | OTP واقعی به موبایل خودتان → ورود به پورتال |
| **تلگرام** (اختیاری) | bot token + webhook | `/start` → لینک chat_id |
| **SMTP** | تأیید تنظیمات فعلی | ارسال ایمیل واقعی (هشدار ریست 2FA) |

🔴 **اگر کلید مودیان آماده نیست:** پایلوت می‌تواند شروع شود، ولی **صورتحساب
رسمی صادر نمی‌شود**. این محدودیت را از روز اول به سازمان پایلوت اعلام کنید،
نه بعد از اولین فاکتور.

## گام ۳ — راه‌اندازی سازمان پایلوت

### ۳.۱ تصمیم اول: دادهٔ آزمایشی پاک شود یا نه؟

```bash
# ⚠️ فقط اگر داده‌های داخل سیستم آزمایشی‌اند
sudo -u postgres pg_dump -d habibazar -F c -f /var/backups/pre-reset-$(date +%Y%m%d-%H%M).dump
cd /var/www/habibazar && npx tsx deploy/reset-erp-data.ts
```
اگر دادهٔ واقعی داخل سیستم است، **این را اجرا نکنید**.

### ۳.۲ ویزارد

`/admin/settings/onboarding` — چک‌لیست راه‌اندازی با لینک مستقیم به هر بخش:
پروفایل شرکت · کدینگ حساب‌ها · دورهٔ مالی · ارز · پروفایل مالیاتی ·
نگاشت `gl_map_*`.

### ۳.۳ کاربران واقعی — اولین آزمون واقعی RBAC 🔴

حداقل سه نقش بسازید (`/admin/users` سپس درخت دسترسی هر کاربر):

| نقش | دسترسی |
|---|---|
| مدیر مالی | ERP کامل + عملیات `:post` و `:void` |
| کارشناس مالی | `write` روی فروش/خرید، **بدون** `:post` |
| کاربر عملیاتی | فقط CRM و انبار |

سپس **با هر سه وارد شوید** و ببینید هرکس دقیقاً همان را می‌بیند که باید.
کارشناس مالی باید بتواند فاکتور بسازد ولی دکمهٔ «ثبت در دفتر» را نداشته باشد.

> قاعدهٔ R5: کاربری که هیچ گرنت درختی ندارد، **دقیقاً مثل نقش قدیمی‌اش** رفتار
> می‌کند. پس کاربران فعلی با این تغییر چیزی از دست نمی‌دهند.

### ۳.۴ فعال‌سازی 2FA

برای هر کاربری که op مالی حساس دارد. هر کاربر QR خودش را اسکن می‌کند و
**کدهای بازیابی فقط یک‌بار نمایش داده می‌شوند** — همان لحظه ذخیره شوند.

### ۳.۵ دادهٔ پایه

حساب‌های بانکی · مراکز هزینه · مشتریان و تأمین‌کنندگان واقعی · کالا/خدمات.

## گام ۴ — چرخهٔ مالی واقعی 🔴 قلب پایلوت

هر گام را با **عدد واقعی** انجام دهید و بعد از هر گام گزارش را نگاه کنید.

| # | کار | چه چیزی را باید ببینید |
|---|---|---|
| ۱ | سند افتتاحیه (مانده‌های اول دوره) | تراز آزمایشی = صفر اختلاف |
| ۲ | فاکتور فروش → تأیید | **پست خودکار GL**: بدهکار ۱۱۰۰ / بستانکار ۴۰۰۰ و ۲۱۰۰ |
| ۳ | ارسال به مودیان (اگر کلید هست) | وضعیت صف: `pending → sent → confirmed` |
| ۴ | دریافت وجه | مانده AR کم می‌شود، بانک زیاد |
| ۵ | فاکتور خرید → تأیید → پرداخت | AP بستانکار می‌شود و بعد صفر |
| ۶ | خزانه: چک، تنخواه، مغایرت‌گیری با صورتحساب واقعی بانک | ردیف‌ها تطبیق می‌خورند و **سابقه در «سابقهٔ مغایرت‌گیری» دیده می‌شود** |
| ۷ | 🔴 یک برگشت روی فاکتور **پرداخت‌شده** | AR باید به صفر برگردد و **هرگز منفی نشود** |
| ۸ | یک ابطال سند | سند اصلی `posted` می‌ماند، سند معکوس هم `posted` — جمع = صفر |
| ۹ | بستن دوره + گزارش‌ها | تراز · سود و زیان · ترازنامه · Aging · معاملات فصلی |
| ۱۰ | 🔴 **تأیید حسابدار** | اعداد با دفاتر دستی/سیستم قبلی می‌خوانند؟ |

🔴 **اگر در هر گام عددی نخواند، همان‌جا توقف کنید.** این مهم‌ترین آزمون کل
پروژه است؛ رد شدن از یک اختلاف کوچک یعنی بقیهٔ پایلوت روی داده‌ای بنا می‌شود
که به آن اعتماد نیست.

## گام ۵ — CRM و پورتال مشتری

1. لید واقعی → فعالیت → تبدیل به مشتری → فاکتور
2. کانبان: کارت را با درگ جابه‌جا کنید **و صفحه را رفرش کنید** — باید سر جای
   جدید بماند. (این دقیقاً همان چیزی است که تا این فاز ذخیره نمی‌شد.)
3. 🔴 **پورتال با یک مشتری واقعی** (`/fa/portal`):
   - OTP پیامکی → ورود
   - فقط فاکتورهای **خودش** را ببیند
   - 🔴 **آزمون IDOR**: آدرس فاکتور مشتری دیگر را دستی در نوار آدرس بزنید →
     باید **۴۰۴** بگیرید، نه فاکتور
   - پرداخت آنلاین → مانده کم شود
4. تیکت پشتیبانی → SLA → escalation
5. کمپین پیامکی فقط به مخاطبانی که **رضایت داده‌اند** + تست لینک انصراف

## گام ۶ — بکاپ و آمادگی بحران

### تست بازیابی واقعی (اجباری، قبل از اتکا به بکاپ)
```bash
sudo bash deploy/restore-drill.sh
```
بکاپ را در یک دیتابیس موقت برمی‌گرداند، تراز آزمایشی را می‌سنجد و **RTO
واقعی** را چاپ می‌کند. سیستم تولید دست نمی‌خورد.

### اگر چیزی خراب شد — طرح بازگشت
```bash
# ۱) برگشت به نسخهٔ قبلی برنامه (بدون دست‌زدن به داده)
sudo bash deploy/deploy-blue-green.sh --rollback

# ۲) اگر داده هم آسیب دید:
sudo -u postgres pg_restore -d habibazar -c /var/backups/<آخرین-بکاپ>.dump
sudo -u hbz pm2 restart habibazar --update-env
sudo bash deploy/post-deploy-check.sh
```

### پایش
- هشدارها: خطای ۵xx · صف مودیان `failed` · نقض SLA · فضای دیسک
- لاگ زنده: `/admin/logs-monitoring` · امنیت: `/admin/soc`

## گام ۷ — ثبت باگ‌های پایلوت

برای هر مشکل این قالب را پر کنید:

```
BUG-XXX
نقش کاربر :
مسیر      : /admin/...
کاری که کردم :
چه انتظاری داشتم :
چه دیدم :
شدت : مسدودکنندهٔ مالی | مسدودکنندهٔ عملیاتی | آزاردهنده | ظاهری
```

**اولویت:** مالی ← عملیاتی ← آزاردهنده ← ظاهری.

🔴 نکتهٔ مهم از تجربهٔ این پروژه: وقتی چیزی «کار نمی‌کند»، **جملهٔ دقیق خطا یا
اسکرین‌شات** را بفرستید. یازده ماژول «خراب» در فاز ۲۶.۲۹ در واقع یک ریشه
داشتند، و آن ریشه فقط از روی پیام واقعی خطا پیدا شد.

## خلاصهٔ دستورها

```bash
# انسداد
sudo bash deploy/fix-db-password.sh --check
sudo bash deploy/fix-db-password.sh --generate
sudo bash deploy/update.sh

# سلامت
sudo bash deploy/post-deploy-check.sh
sudo bash deploy/post-deploy-check.sh --json > /tmp/health.json

# بکاپ و بازیابی
sudo -u postgres pg_dump -d habibazar -F c -f /var/backups/manual-$(date +%Y%m%d-%H%M).dump
sudo bash deploy/restore-drill.sh
sudo bash deploy/deploy-blue-green.sh --rollback

# وضعیت
sudo -u hbz pm2 status
sudo -u hbz pm2 logs habibazar --lines 100
curl -s localhost:3000/api/health?probe=deep | head -c 400
```
