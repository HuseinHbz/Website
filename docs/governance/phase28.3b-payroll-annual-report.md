## 2. 🔴 چرا «پایهٔ سنوات» و «سنوات پایان خدمت» از هم جدا نگه داشته شدند

دو چیز کاملاً متفاوت یک نام فارسی مشترک دارند:

| | پایهٔ سنوات | سنوات پایان خدمت |
|---|---|---|
| چیست | مزایای **ماهانه** | مزایای **ترک خدمت** |
| کجا | `payroll_earning_types` (۲۸.۳-الف) | `payroll_severance_calculations` |
| ورودی | مبلغ ماهانه | مبنای **روزانه** + مدت خدمت |

این تنها خطای این حوزه است که **سال‌ها نامرئی می‌ماند**: عدد ماهانه درست به‌نظر
می‌رسد، رقم پایان خدمت تا وقتی کسی واقعاً نرود بررسی نمی‌شود، و آن موقع یا شرکت
سال‌ها کم پرداخته یا بدهی را بیش از واقع ذخیره کرده.

جداسازی فقط در مستندات نیست، **در امضای تابع** است: `calculateSeverance` یک
مبنای **روزانه** و یک بازهٔ خدمت می‌گیرد، پس یک مزایای ماهانه را نمی‌شود
اشتباهی به آن پاس داد.

اثبات زنده:

```
✅ «پایهٔ سنوات» exists as a MONTHLY earning type (28.3-الف)
✅ the Eid base is read from the earnings flagged in_eid_base — 252000000
✅ the severance base is read from the earnings flagged in_severance_base — [200000000,...]
✅ 🔴 the two bases are DIFFERENT — eid 252000000 vs severance 200000000
✅ 🔴 service days come from the append-only history, not from a slip — 1311
✅ 🔴 the severance figure is NOT the monthly seniority allowance — 718000000 vs 200000000
```

### باگی که همین ادعا را نزدیک بود از دست بدهد

اجرای اول، مبنای سنوات را **۲۵۲٬۰۰۰٬۰۰۰** برگرداند — دقیقاً مبنای عیدی.

علت: شرط `in_severance_base=1` را در **شرط JOIN** گذاشته بودم، نه داخل جمع. یک
`LEFT JOIN` که match نشود سطر را حذف نمی‌کند، پس آن شرط عملاً هیچ‌چیز را فیلتر
نمی‌کرد و همهٔ اقلام درآمدی بی‌صدا شمرده می‌شدند. اصلاح:
`SUM(CASE WHEN t.id IS NOT NULL THEN l.amount ELSE 0 END)`.

اگر سوئیت فقط کد را می‌خواند این را نمی‌دید — کوئری کاملاً منطقی به‌نظر می‌رسد.

## 3. عیدی — شکل محاسبه

استحقاق = N روز از مزد خودِ کارمند (از اقلام flag‌دار) × نسبت روزهای خدمت در
سال، سپس محدود بین کف و سقفی که **هر دو بر حسب روزِ حداقل مزد** تعریف شده‌اند.

🔴 **همین بند آخر معمولاً غافلگیر می‌کند**: سقف مضربی از حقوق خودِ فرد نیست. با
حداقل مزد ۱۴۰۵، سقف ۴۹۸٬۷۶۶٬۵۰۰ ریال است — پس هر مبنای بالاتر از حدود ۲۵۰
میلیون ریال دقیقاً همان سقف را می‌گیرد. یک تست واحد این واقعیت را صریحاً قفل
کرده تا کسی بعداً فکر نکند باگ است.

کف و سقف هم **به تناسب** کم می‌شوند: کسی که سه ماه کار کرده یک‌چهارم کف را
می‌گیرد، نه تمامش.

🔴 **ذخیره آزاد می‌شود، دوباره هزینه نمی‌شود.** اگر ماه‌به‌ماه ذخیره گرفته
شده، هزینه‌اش قبلاً شناسایی شده؛ شارژ دوبارهٔ کل مبلغ در پایان، هزینه را دو
برابر می‌کرد. اثبات زنده:

```
✅ 🔴 only the SHORTFALL hits expense — the provision is released, not double-charged
   expense +583,561,644 of 600,000,000 (ذخیرهٔ انباشته ۱۶٬۴۳۸٬۳۵۶)
✅ 🔴 the provision account carries a liability — -49,315,068
✅ 🔴 re-running the same month accrues nothing — idempotent
✅ 🔴 the trial balance still ties out after the whole annual cycle
```

**ذخیرهٔ ماهانه پیش‌فرض خاموش است.** شناسایی تدریجی بدهی از نظر حسابداری
درست‌تر است، ولی تصمیمش سیاست شرکت است و روی وضعیت مالیاتی اثر دارد — سیستم
به‌جای شما فرض نمی‌گیرد و اجرا را با پیام صریح رد می‌کند تا خودتان روشنش کنید.

## 6. ⚠️ خروجی‌های قانونی — `blocked-external`

سه قالب ساخته شد: **لیست بیمه (DSK)**، **لیست مالیات حقوق**، و **خلاصهٔ دوره**.

🔴 **ترتیب ستون‌های دو قالب اول با فایل واقعی سامانه تطبیق داده نشده است.**
حدس‌زدن فرمت بی‌معنی بود، پس به‌جای آن:

- ترتیب ستون‌ها **داده** است نه کد (`payroll_export_layouts.columns`) — اگر
  اشتباه بود، بدون انتشار نسخهٔ جدید اصلاح می‌شود
- هر قالب پرچم `verified` دارد که **پیش‌فرض صفر** است
- UI یک هشدار زرد صریح نشان می‌دهد و دانلود هدر `X-Layout-Verified: 0` می‌فرستد،
  تا اسکریپتی که فایل را می‌گیرد هم بفهمد تأیید نشده
- بعد از تطبیق با سامانه، اپراتور «با سامانه تطبیق دادم» را می‌زند

اثبات زنده:

```
✅ 🔴 the statutory layouts are marked UNVERIFIED with a reason
✅ 🔴 the render reports that the layout is not verified
✅ 🔴 the column order is DATA — reordering the layout changes the file
✅ a missing key never becomes the text "undefined"
✅ an unknown layout is refused, not guessed
```

یک جزئیات کوچک ولی مهم: کلیدی که در داده نباشد به **فیلد خالی** تبدیل می‌شود،
نه به متن `undefined`. فایلی که سامانه رد کند بهتر از فایلی است که قبول کند و
داخل یک ستون آشغال داشته باشد.

## 7. ⛔ تأیید حسابدار — گرفته نشده

همان الزام ۲۸.۳-الف، اینجا هم برقرار است. §4 هفت محاسبهٔ عیدی و چهار محاسبهٔ
سنوات با اعداد واقعی دارد تا حسابدارتان جزء‌به‌جزء بسنجد.

مواردی که مخصوصاً ارزش بررسی دارند:

1. **سقف عیدی** — تفسیر ما: ۹۰ روزِ حداقل مزد، پیش از ضرب در نسبت کارکرد. اگر
   بخشنامهٔ سازمان شما جور دیگری می‌گوید، هر سه عدد پارامترند.
2. **مالیات عیدی** — `eid_tax_exempt_amount` پیش‌فرض صفر گذاشته شده، یعنی عیدی
   کاملاً مشمول. اگر معافیتی هست، مقدارش را وارد کنید.
3. **مبنای سنوات** — «آخرین ماه» پیش‌فرض است. اگر سیاست شما میانگین است، یک
   پارامتر عوض می‌شود.
4. **ذخیرهٔ ماهانهٔ سنوات** — روشن یا خاموش، تصمیم حسابدار.
5. **سقف بازخرید مرخصی** — ۹ روز پیش‌فرض گذاشته شده؛ عدد قراردادی است نه قانونی.
