# راهنمای سیستم دسترسی درختی (RBAC + ABAC) — فاز 26.27

این راهنما برای مدیر سیستم است: چطور به یک کاربر، جز به جز و دقیقاً همان‌قدر که لازم دارد، دسترسی بدهید.

## درخت دسترسی چیست؟
دسترسی‌ها مثل یک درخت چیده شده‌اند:

```
ورک‌اسپیس (erp)
 └── ماژول (erp.finance — مرکز مالی)
      └── تب (erp.finance.journal — اسناد حسابداری)
           └── عملیات حساس (erp.finance:post — پست سند)
```

هر گره **مستقل** سه حالت دارد:
- **منع (none)** — کاربر آن بخش را نه می‌بیند نه می‌تواند بخواند. کل زیرشاخه هم قفل می‌شود، حتی اگر پایین‌تر «ویرایش» داده باشید.
- **خواندن (read)** — دیدن و گزارش‌گیری؛ هر تلاش نوشتن از سمت سرور ۴۰۳ می‌گیرد.
- **ویرایش (write)** — ایجاد/ویرایش رکوردهای عادی. **عملیات حساس را شامل نمی‌شود.**

### قواعد تصمیم (به همین ترتیب)
1. **منع غالب است:** «منع» صریح در هر سطح، همهٔ زیرشاخه را می‌بندد.
2. **خاص‌ترین برنده است:** تنظیم روی تب، بر تنظیم ماژول و ورک‌اسپیس اولویت دارد.
3. **ارث‌بری:** گرهٔ بدون مقدار، مقدار والدش را می‌گیرد (در UI کم‌رنگ + «از … ارث‌برده»).
4. **بدون هیچ تنظیم:** کاربر دقیقاً رفتار نقش پایه‌اش (super_admin/administrator/editor/auditor/viewer) را دارد — مثل قبل از این فاز.

## عملیات حساس (op)
«ویرایش» یعنی کار روزمره؛ عملیات‌هایی که اثر مالی/امنیتی برگشت‌ناپذیر دارند **کلید جدا** می‌خواهند:
پست سند (:post)، ابطال (:void)، تأیید فاکتور (:confirm)، برگشت (:return)، بستن دوره (:close_period)،
تأیید/رد/تفویض تأییدیه، ارسال مودیان (:submit)، ساخت کاربر/تغییر نقش/ریست 2FA/ویرایش دسترسی و … .

نمونهٔ رایج: **کارشناس مالی** ژورنال را «ویرایش» دارد و سند پیش‌نویس می‌سازد، ولی بدون
`erp.finance:post` نمی‌تواند پست کند — پست با مدیر مالی است (تفکیک وظایف).

## چطور دسترسی بدهم؟ (گام به گام)
1. **کاربران** → ردیف کاربر → عمل **Permissions** (یا مستقیم `/admin/users/<id>/permissions`).
2. یا از یک **قالب نقش** شروع کنید (یک کلیک) و بعد سفارشی کنید، یا گره به گره تنظیم کنید.
3. روی هر گره یکی از سه حالت را بزنید؛ برای بازگشت به ارث‌بری دکمهٔ «بازگشت به ارث‌بری».
4. زیر ماژول‌های دارای عملیات حساس، چک‌باکس هر op را جدا بزنید.
5. با «این کاربر چه می‌بیند» خروجی منو را پیش‌نمایش بگیرید.
6. برای کاربر مشابه قبلی: «کپی دسترسی از کاربر دیگر».
7. خروجی حسابرسی: صفحهٔ ماتریس کاربران×ماژول‌ها + دانلود CSV.

هر تغییر دسترسی با نام تغییردهنده، زمان، مقدار قبلی و جدید در `rbac_audit` ثبت می‌شود.

## قالب‌های نقش آماده
| قالب | محتوا |
|---|---|
| مدیرعامل | همهٔ داشبوردها و ماژول‌ها read |
| مدیر مالی | ERP کامل + همهٔ opهای مالی؛ system/backup منع |
| کارشناس مالی | مالی/فروش/خرید write **بدون** :post و :confirm |
| حسابرس | همه‌چیز read + لاگ‌ها؛ هیچ op |
| مدیر منابع انسانی | سازمان write |
| مدیر مارکتینگ | CRM/برند/محتوا write |
| مدیر IT | system/security/backup/operations write |
| سهامدار | فقط داشبورد اجرایی و گزارش کلان؛ باقی منع |
| کارمند | داشبورد + تیکت‌های خودش (scope=own) |

## دامنهٔ سطر (ABAC — scope)
در درخت دسترسی، کنار ماژول‌هایی که پشتیبانی واقعی دارند یک انتخابگر «دامنهٔ سطر» هست:
- **همه (all)** — پیش‌فرض، دقیقاً رفتار امروز
- **فقط خودم (own)** — فقط رکوردهایی که مالکشان خود کاربر است
- **واحد من (department)** — رکوردهای هم‌واحدی‌ها (بر اساس فیلد «واحد» کاربران)

دامنه **سمت سرور و داخل WHERE کوئری** اعمال می‌شود، نه فیلتر ظاهری؛ و دسترسی مستقیم به
شناسهٔ رکورد خارج از دامنه **۴۰۴** می‌دهد (وجود رکورد هم لو نمی‌رود).

ماژول‌های پشتیبانی‌شده (26.28): **CRM (لیدها + فعالیت‌ها)** · **تیکت‌ها** · **مشتری ۳۶۰** ·
**اسناد فروش** (مالک = مالک مشتری، وگرنه سازنده) · **پروژه‌ها**. دامنهٔ «شرکت» عمداً ارائه
نشده چون زیرساختش (company روی کاربر) وجود ندارد — انتخابگر فقط چیزی را نشان می‌دهد که
واقعاً اجرا می‌شود.

فیلد حساس: کاربرِ دسترسی‌محور بدون `erp.inventory:cost_view` بهای تمام‌شده/ارزش موجودی را
در پاسخ API اصلاً دریافت نمی‌کند (کلید از payload حذف می‌شود — هم فهرست کالاها، هم داشبورد
انبار). حذف واقعی است، نه مخفی‌سازی CSS.

## 2FA (احراز دومرحله‌ای)
- فعال‌سازی: کاربران → ستون 2FA → اسکن QR → کد ۶رقمی. بعد از فعال‌سازی **۱۰ کد بازیابی
  یک‌بارمصرف** فقط همان لحظه نمایش داده می‌شود — چاپ/ذخیره کنید.
- گم‌شدن گوشی: ورود با یکی از کدهای بازیابی (هر کد یک‌بار)؛ ایمیل هشدار می‌آید. بعد 2FA را
  ریست/دوباره فعال کنید.
- ریست 2FA دیگری: نیازمند op «security.users:reset_2fa»؛ به خود کاربر ایمیل اطلاع می‌رود.
- سیاست سخت‌گیرانه (اختیاری): در erp_settings کلید `2fa_required_sensitive=1` → هر op مالی
  حساس بدون 2FA فعال ۴۰۳ می‌گیرد.
- امنیت داخلی: راز TOTP رمزنگاری‌شده (AES-256-GCM) ذخیره می‌شود؛ کد تکراری در همان پنجره رد
  می‌شود؛ ۵ تلاش غلط = ۱۰ دقیقه قفل.

## نکات فنی (برای توسعه‌دهنده)
- هر روت ادمین باید `requirePermission('<key>', 'read'|'write', legacyAction?)` صدا بزند —
  گیت `audit:rbac` بدون آن build را می‌شکند. کلید فقط در کد روت (نه هدر/URL/بدنه).
- op حساس داخل همان شاخه: `requireOp(user, '<module>:<op>', legacyAction?)`.
- ماژول/تب جدید در `workspaces.ts` خودکار گرهٔ درخت می‌گیرد؛ op جدید را در `SENSITIVE_OPS`
  (registry.ts) ثبت کنید.
