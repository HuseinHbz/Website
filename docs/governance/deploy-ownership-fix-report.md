# 26.30-fix-ownership — رفع ریشه‌ای مشکل مالکیت فایل در `deploy/update.sh`

> **صداقت دربارهٔ دامنهٔ این گزارش.** بندهای ۰، ۱ و ۲ به‌طور کامل روی این
> محیط توسعه انجام و با یک محیط شبیه‌سازی‌شدهٔ واقعی (کاربر غیر-root جدا،
> دقیقاً همان مدل مجوز فایل لینوکس) اثبات شدند — نه فرض. بند ۳ (بررسی
> patch) و بخشی از بند ۴ (اجرای واقعی `update.sh` روی سرور تولید) نیازمند
> دسترسی SSH به سرور است که این نشست آن را ندارد؛ دستورهای دقیق برای
> نگهدارنده در §5 و §6 آمده تا خودش این دو بند را ببندد.

## 2. 🔴 ریشهٔ دقیق (بند ۰)

self-heal نسخهٔ قبلی این شکل بود:

```bash
if [[ -n "$(find "$APP_DIR" … -prune -o \! -user "$APP_USER" -print -quit …)" ]]; then
  chown -R "$APP_USER":"$APP_USER" "$APP_DIR"
fi
```

دو ضعف واقعی داشت:

1. **تشخیص شرطی، یک‌بار، فقط در ابتدای اسکریپت.** بین لحظهٔ تشخیص و لحظهٔ
   واقعیِ `git reset --hard` (که چند مرحله بعدتر اجرا می‌شود: تعیین شاخه،
   بروزرسانی `.env.local`، `git fetch`…) هیچ تضمینی نبود که مالکیت دست‌نخورده
   بماند — یک `git pull` دستیِ موازی (دقیقاً چیزی که در حادثه اتفاق افتاد،
   طبق شواهد لاگ) می‌توانست بین این دو لحظه فایل جدید با مالکیت `root` بسازد.
2. **`-quit` به‌محض اولین مورد متوقف می‌شود** — این خودش مشکلی ندارد چون در
   صورت پیدا شدن هر مورد، `chown -R` روی کل درخت اجرا می‌شد (نه فقط آن یک
   فایل) — اما چون بند ۱ (تشخیص یک‌باره) اصل مشکل بود، این جزئیات اهمیت
   ثانویه داشت.

## 3. 🔴 بازتولید (شاهد واقعی، نه فرض)

با یک کاربر لینوکسی غیر-root واقعی (`hbztest`، معادل `hbz`) و یک مخزن git
واقعی (نه شبیه‌سازی نظری)، دو سناریو بازتولید شد:

**سناریوی الف — فایل موجود با مالکیت اشتباه:**
```
$ sudo -u hbztest git reset --hard origin/main
error: unable to unlink old 'src/app/admin/existing.txt': Permission denied
fatal: Could not reset index file to revision 'origin/main'.
```

**سناریوی ب — پوشهٔ جدید زیر یک پدرِ ازقبل‌ناهم‌مالک (دقیقاً حادثهٔ فاز ۲۸.۵):**
کلون محلی در commit اول بود (پوشهٔ `recruitment/` هنوز وجود نداشت)، پدرِ آن
(`src/app/admin`) مالکیت `root` گرفت، سپس تلاش برای رسیدن به commit بعدی
(که `recruitment/Center.tsx` را اضافه می‌کند) با همان خطا شکست:
```
$ sudo -u hbztest git reset --hard d321811
error: unable to unlink old 'src/app/admin/existing.txt': Permission denied
```
(git ابتدا باید فایل‌های موجود زیر همان پدر را دوباره بنویسد؛ چون پدر
ناهم‌مالک است، حتی رسیدن به پوشهٔ جدید هم شکست می‌خورد — این دقیقاً تأیید
می‌کند مشکل در سطح «پوشهٔ پدر»، نه صرفاً «فایل تک‌تک» است.)

## 4. 🔴 راه‌حل اعمال‌شده

```bash
heal_ownership() {
  sudo find "$APP_DIR" -mindepth 1 \
    \( -path "$APP_DIR/node_modules" -o -path "$APP_DIR/.git" -o -path "$APP_DIR/.next" \) -prune \
    -o -exec chown "$APP_USER":"$APP_USER" {} +
}
```

فراخوانی **بدون قید و شرط** (نه پشت یک `if` تشخیصی) در دو نقطه:

```bash
step "ترمیم مالکیت کلون پیش از fetch..."
heal_ownership
… git fetch …

step "ترمیم مالکیت کلون پیش از reset --hard..."
heal_ownership
… git reset --hard …
```

نکات طراحی:
- بدون `-type f` — روی خودِ پوشه‌ها هم اجرا می‌شود (نه فقط فایل‌های داخلشان).
- `node_modules`/`.git`/`.next` حذف می‌شوند تا هزینه پایین بماند؛ اینها هرگز
  توسط git دست‌کاری نمی‌شوند، پس نیازی به ترمیم مالکیتشان در این نقطه نیست.
- idempotent: روی درخت سالم، `chown` هرکدام از فایل‌ها را به همان مالک
  فعلی‌شان می‌نویسد — بی‌اثر و ارزان.

**اثبات با هر دو سناریوی §۳، این‌بار با فراخوانی `heal_ownership` پیش از
هر تلاش:**
```
$ heal_ownership
$ sudo -u hbztest git reset --hard origin/main
HEAD is now at 4c37204 init                          ← موفق

$ chown root:root src/app/admin   # شبیه‌سازی یک درهم‌ریختگی دوباره
$ heal_ownership
$ sudo -u hbztest git reset --hard d321811
HEAD is now at d321811 add recruitment                ← موفق، پوشهٔ جدید هم رسید
```

## 5. بند ۳ — بررسی patch کنارگذاشته‌شده (نیازمند اقدام نگهدارنده)

این نشست به سرور تولید دسترسی ندارد. روی خودِ سرور اجرا کنید:

```bash
# آیا این patch فقط بازتولید همان تغییراتی است که از قبل در ریپو هست؟
git -C /var/www/habibazar diff HEAD --stat  \
  <(git -C /var/www/habibazar show HEAD:) 2>/dev/null || true

# راه ساده‌تر: خودِ فایل را با آخرین commit مقایسه کنید
cat /root/habibazar-local-changes-20260810-030047.patch | head -100
```

اگر محتوای patch فقط نسخهٔ قدیمی‌تر فایل‌هایی است که همین الان در ریپو با
مالکیت درست وجود دارند (محتمل‌ترین حالت — چون این تغییرات محلی، نتیجهٔ
همان اجرای ناموفق قبلی بودند، نه ویرایش دستیِ عمدی)، حذف امن است:
```bash
rm /root/habibazar-local-changes-20260810-030047.patch
```
اگر تفاوت واقعی و عمدی در آن دیدید (چیزی که هیچ کامیتی در ریپو ندارد)،
جداگانه (نه در این گزارش) بررسی و در صورت لزوم به‌عنوان یک commit مجزا
اعمال کنید — هرگز مستقیم روی کلون سرور.

## 6. بند ۴ — چک‌لیست اجرای واقعی (نگهدارنده روی سرور اجرا کند)

```bash
cd /var/www/habibazar
sudo bash deploy/update.sh
```

انتظار: بدون خطای Permission denied، تا انتهای build و `pm2 reload` کامل
پیش برود. سپس:

```bash
# نسخهٔ مستقر باید همان آخرین commit این branch باشد
git -C /var/www/habibazar log -1

# health check
bash deploy/health-check.sh   # یا: deploy/post-deploy-check.sh در صورت وجود

# idempotency — بلافاصله دوباره اجرا کنید؛ باید بدون خطا و بدون
# "commit جدیدی نیست" (چون همین الان به‌روز شد) به شما بگوید
sudo bash deploy/update.sh
```

سپس در مرورگر:
- `https://<domain>/admin/recruitment`
- `https://<domain>/admin/training`
- `https://<domain>/admin/reviews`

هرکدام باید با ورود ادمین باز شوند (نه ۴۰۴/۵۰۰).

## 7. Gates
