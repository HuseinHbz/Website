# DEPLOY-FIX-2 — رفع ریشه‌ای بحران مالکیت فایل در استقرار (نه وصلهٔ سوم)

> **صداقت دربارهٔ دامنهٔ این گزارش.** بندهای ۰ (تحلیل از روی لاگ‌های واقعی
> پیوست‌شده توسط نگهدارنده)، ۱، ۲ و ۴ کامل انجام و — جایی که ادعای رفتاری شد —
> با بازتولید واقعی (یک ریپوی git واقعی با دو برنچ نامرتبط، یا یک کاربر لینوکسی
> غیر-root واقعی) اثبات شدند، نه فرض. **بند ۳ (یک اجرای کامل و موفق
> `update.sh` روی سرور تولید) نیازمند دسترسی SSH به سرور است که این نشست آن
> را ندارد و ندارد بوده — این فاز طبق قانون بستن خودش (closing_rule) هنوز
> بسته نیست تا نگهدارنده خودش این اجرا را انجام دهد و خروجی را برگرداند.**
> هیچ ردیفی در جدول اقرار زیر ✅ نشده مگر شاهد واقعی داشته باشد؛ بند ۳ آگاهانه
> 🟡 نگه داشته شده.

## 2. 🔴 بند ۰ — چرا مالکیت اصلاً به‌هم می‌ریزد

بدون SSH به سرور، اجرای واقعی `find /var/www/habibazar ! -user hbz` روی این
نشست ممکن نیست. آنچه **از روی شواهد واقعی موجود** (لاگ‌های کامل سه اجرای
`update.sh` که نگهدارنده مستقیم پیست کرد) قابل تحلیل قطعی بود:

### علت مستقیم حادثهٔ سوم (`EACCES` روی `.next/trace`)

خطِ snapshot قدیمی:
```bash
cp -r "$WEB_DIR/.next" "$WEB_DIR/.next.bak"   # بدون sudo -u — با مالکیت root اجرا می‌شد
```
کل `update.sh` زیر `sudo bash` (یعنی به‌عنوان `root`) اجرا می‌شود؛ این خط تنها
جایی بود که استثنائاً `sudo -u hbz` نداشت. یک `cp` معمولی هنگام اجرا توسط
`root`، مالکیت مبدأ را حفظ **نمی‌کند** — فایل‌های کپی‌شده مالک‌شان `root`
می‌شود. اگر پیش‌تر یک build شکست می‌خورد و rollback (`mv .next.bak → .next`)
اجرا می‌شد، `.next` زندهٔ سایت برای همیشه `root`-مالک می‌ماند — و از آن به بعد
هر build بعدی که با `sudo -u hbz` اجرا می‌شد دقیقاً همین `EACCES` را می‌داد.
این با رفع اول (`4fd40e5`: فقط `chown -R` روی `.next` موجود) کامل بسته نشد —
نگهدارنده تأیید کرد که حتی بعد از آن رفع، همان خطا تکرار شد؛ علت دقیقِ اینکه
چرا خودِ `chown` کافی نبود بدون SSH قابل ریشه‌یابی نیست (احتمال: یک فایل
باقی‌ماندهٔ قفل‌شده از یک build نیمه‌کاره، یا مالکیت تودرتوی غیرمعمول). به همین
دلیل در `a3ff58d` رویکرد کلاً عوض شد: به‌جای تعمیر یک `.next` با تاریخچهٔ
نامعلوم، snapshot گرفته می‌شود (و صریحاً `chown` می‌شود) و خودِ `.next` زنده
**کامل حذف** می‌شود — build روی یک `.next` تازه که از لحظهٔ ساخت `hbz`-مالک
است اجرا می‌شود. این فاز (DEPLOY-FIX-2) این رویکرد را حفظ و مستندسازی کرد؛
تغییر کد اضافه‌ای در این نقطهٔ خاص لازم نبود چون از پیش درست پیاده شده بود.

### آیا کسی دستور مستقیم زده بود؟

بله — ولی نه یک انسان. لاگ دوم که نگهدارنده پیست کرد این را نشان می‌دهد:

```
root@HBZ:/var/www/habibazar# git pull
...
fatal: Need to specify how to reconcile divergent branches.
root@HBZ:/var/www/habibazar# sudo bash deploy/update.sh
```

نگهدارنده مستقیم `git pull` دستی زد (که هشدار قرمزِ خودِ اسکریپت صریحاً منع
کرده بود) — اما این دستور با خطا **متوقف شد** (هیچ merge/commit ای انجام
نداد، چون git بدون استراتژی مشخص کاری نکرد)، پس خودش عامل درفتِ مالکیت این
حادثهٔ خاص نبود. عامل واقعیِ پیام «diverged» که در همان اجرا ظاهر شد، یک نقص
منطقی در خودِ `update.sh` بود — تحلیل کامل در §4.

**نتیجه**: عادت انسانی (اجرای `git pull` دستی) واقعاً رخ داده و باید متوقف
شود (رفع در §3 — هشدار حالا در همان اولین لحظهٔ اجرا چاپ می‌شود، نه فقط در
لاگ)، ولی علتِ خودِ حادثهٔ EACCES و علتِ خودِ پیام divergent هرکدام یک نقص جدا
در کدِ خودِ اسکریپت بودند، نه یک کامیت دستیِ انسانی روی سرور.

## 3. 🔴 بند ۱ + ۲ — self-heal کامل + پیشگیری

### گسترش پوشش self-heal (R3 — کل خانوادهٔ مشکل، نه یک نمونه)

| مسیر | نقطهٔ ترمیم | مکانیزم |
|---|---|---|
| کل سورس (بجز `node_modules`/`.git`/`.next`) | پیش از `git fetch` **و** پیش از `git reset --hard` (دو نقطه، از 26.30) | `heal_ownership()` — بی‌قید-و-شرط |
| `.next` | پیش از build | snapshot (`chown` صریح) + حذف کامل + بازسازی از صفر توسط خودِ build (از `a3ff58d`) |
| `node_modules` | درست پیش از اجرای واقعی `npm ci` (نه در مسیر «تغییر نکرده») | `chown -R` — **جدید در این فاز** |
| `public/uploads` و بقیهٔ سورس | همان `heal_ownership()` بالا (این مسیر از prune مستثنی نیست) | بدون تغییر — از قبل پوشش داشت |
| `/home/hbz/logs` | انتهای اسکریپت | `chown -R` — از قبل موجود بود |

### ثبت drift به‌جای ترمیم بی‌صدا (بند ۲)

پیش از هر ترمیمی، یک `find` سریع می‌شمارد چند مسیر (بجز `node_modules`/`.git`/
`.next`) مالک درستی ندارند و — اگر عدد بزرگ‌تر از صفر بود — جزئیات را به
`/var/log/habibazar-ownership-drift.log` اضافه می‌کند (timestamp + تعداد +
لیست مسیر:مالک). این لاگ **جدا** از لاگ هر اجراست تا با گذشت زمان بتوان الگوی
تکرار را دید (چند بار، کِی، چقدر) — بدون این، هر بار self-heal «بی‌صدا» مشکل
را می‌پوشاند و کسی نمی‌فهمد چند بار واقعاً رخ داده.

### هشدار در همان لحظهٔ اول

پیام «هرگز دستی روی این کلون…» قبلاً فقط بعد از تشخیص برنچ default چاپ
می‌شد (چند مرحله داخل اسکریپت). حالا بلافاصله بعد از تأیید وجود کلون — قبل از
هر مرحلهٔ دیگر — چاپ می‌شود؛ همراه با یک هشدار مشابه در بالای خودِ فایل
`update.sh` (کامنت)، `deploy/README.md` (یک بلاک برجسته در همان خط اول)، و
یک قانون جدید در `CLAUDE.md`.

## 4. 🔴 بند ۴ — ریشهٔ واقعی «Divergent branches»

لاگ دوم نگهدارنده نشان می‌داد:
```
Your branch and 'origin/claude/bold-lamport-a1d6tg' have diverged,
and have 3 and 2 different commits each, respectively.
```

### تحلیل

بین دو اجرای `update.sh`، default branch مخزن در گیت‌هاب از `V3-Codex` به
`claude/bold-lamport-a1d6tg` عوض شده بود. در اجرای اول بعد از این تغییر، برنچ
محلی `claude/bold-lamport-a1d6tg` تازه ساخته شد (`checkout -f -B ... origin/...`)
و درست هم‌راستا با remote بود — اما همان اجرا با شکست build مواجه شد و کد
rollback قدیم این را اجرا کرد:
```bash
git reset --hard "$PREV_COMMIT"   # روی برنچ فعلی — که حالا claude/bold-lamport-a1d6tg است
```
`$PREV_COMMIT` کامیتی بود که HEAD **قبل از این اجرا** رویش بود — یعنی متعلق به
تاریخچهٔ برنچ **قبلی** (`V3-Codex`)، نه `claude/bold-lamport-a1d6tg`. ریست‌کردن
برنچِ تازه‌ساخته‌شده به کامیتی از یک تاریخچهٔ کاملاً نامرتبط، دقیقاً همان چیزی
تولید می‌کند که git «diverged» می‌بیند.

### بازتولید واقعی

یک ریپوی git واقعی با دو برنچ کاملاً بی‌ربط (`V3-Codex` و `bold-lamport`)
ساخته و همین توالی دقیق (checkout به برنچ جدید → «build» فرضی شکست → rollback
قدیم) اجرا شد:
```
=== OLD buggy rollback: reset --hard $PREV_COMMIT on current branch ===
## bold-lamport...origin/bold-lamport [ahead 1, behind 2]
```
دقیقاً همان الگوی لاگ واقعی سرور بازتولید شد. سپس با کد جدید (rollback به
خودِ `$PREV_BRANCH` وقتی با `$BRANCH` فرق دارد):
```
=== NEW fix: checkout back to PREV_BRANCH instead ===
Your branch is up to date with 'origin/V3-Codex'.
bold-lamport branch untouched, still points at origin tip: fc70178
```
هیچ برنچی دیگر آلوده نمی‌شود.

### آیا خطرناک بود؟

نه به‌صورت عملکردی — اجرای *بعدی* `update.sh` با `git reset --hard
origin/$BRANCH` همیشه دوباره برنچ را با remote یکی می‌کرد (خودِ لاگ سوم این را
نشان می‌دهد: «HEAD is now at 4fd40e5»، یعنی خودش رفع شد). ولی گمراه‌کننده و
نشانهٔ یک نقص واقعی بود — حالا رفع شده تا دیگر اصلاً رخ ندهد.

## 5. تغییرات فایل

- `deploy/update.sh`: هشدار زودهنگام + حسابرسی/لاگ drift + heal برای
  `node_modules` + رفع rollback عبور از مرز برنچ.
- `deploy/README.md`: بلاک هشدار برجسته در ابتدا + بخش‌های جدید برای
  `node_modules` و divergent-branches.
- `CLAUDE.md`: قانون جدید در بخش Deploy.

## 6. 🔴 بند ۳ — چک‌لیست برای نگهدارنده (اجرای واقعی روی سرور)

این فاز طبق `closing_rule` تا این مرحله بسته **نیست**. مراحل:

1. `git pull` **نکنید** — مستقیم بزنید:
   ```
   sudo bash deploy/update.sh
   ```
2. خروجی کامل (از «دریافت آخرین تغییرات» تا «سرویس پاسخ می‌دهد ✓») را کپی
   کنید و برگردانید — از جمله اگر `heal_ownership`/drift-log چیزی گزارش داد.
3. اگر build موفق شد: در مرورگر یک صفحهٔ ادمین ERP (مثلاً `/admin/finance`) و
   یک صفحهٔ HR (`/admin/hr` یا معادل) را باز کنید و تأیید کنید داده واقعی نشان
   می‌دهند (نه فقط build سبز).
4. اگر باز هم شکست خورد: خروجی کامل + محتوای
   `/var/log/habibazar-ownership-drift.log` را بفرستید — چون این فاز تمام
   خانوادهٔ شناخته‌شدهٔ مشکل را می‌بندد، ولی اگر یک مسیر ناشناختهٔ دیگر هم درفت
   کرده باشد، آن لاگ دقیقاً نشان می‌دهد کدام است.

## 7. Gates

این یک تغییر فقط-deploy است (بدون کد اپلیکیشن): `bash -n deploy/update.sh`
تمیز؛ TS/ESLint/audits/build اپلیکیشن دست‌نخورده و بدون نیاز به اجرای مجدد.
