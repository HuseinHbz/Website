## 2. اسکریپت سلامت‌سنجی، همان اجرای اول، سه باگ پیدا کرد

این دقیقاً همان الگویی است که فاز ۲۶.۲۹ را تعریف کرد: ابزار را ساختم، اجرا

### ۲.۱ سه باگ در خودِ اسکریپت (پیدا شده با اجرا، نه بازبینی)

| باگ | چه شد | رفع |
|---|---|---|
| `%{http_code}` به‌صورت `000000` چاپ می‌شد | `curl` خودش روی شکست `000` می‌دهد و `\|\| echo 000` یک `000` دوم **الحاق** می‌کرد؛ نتیجه با هیچ شرطی مطابقت نمی‌کرد | یک تابع `http()` واحد |
| مقایسهٔ عددی می‌شکست | `wc -c` مقدار `"0\n0"` می‌داد | `tr -d ' \n'` + بررسی `^[0-9]+$` |
| وب‌هوکِ مرده «باز» گزارش می‌شد | `000` در شرطِ «باز است» می‌افتاد | `000` حالا صریحاً شکست است |

### ۲.۲ یک باگ واقعی در محصول: سه صفحهٔ عمومی با قطع دیتابیس ۵۰۰ می‌دادند

اسکریپت با دیتابیسِ لحظه‌ای‌قطع‌شده اجرا شد و نشان داد:


در حالی که `/events`, `/docs`, `/products`, `/about`, `/` همگی ۲۰۰ می‌دادند —

## 3. 🔴 BUG-206 — ریشهٔ واقعی پیدا شد، و یک ادعای من در ۲۶.۳۳ اصلاح می‌شود

### تصحیح

در فاز ۲۶.۳۳ نوشتم «رفع تأیید شده — درگ واقعی `PUT {"status":"qualified"}` را
شلیک می‌کند». **این ادعا بیش از حد قوی بود.** من *درخواست* را دیده بودم، نه
*ذخیره‌شدن* را. در این فاز مستقیم به دیتابیس نگاه کردم:

```
id |      name       | status
27 | E2E Kanban Lead | new      ← با وجود اینکه PUT شلیک شده بود
```

### ریشهٔ واقعی

کانبان برای جابه‌جایی فقط `{id, status}` می‌فرستد، ولی روت `PUT` **همان schema
ساخت** را استفاده می‌کرد که `name` را اجباری کرده بود:

```bash
PUT /api/admin/crm/leads  {"id":27,"status":"qualified"}
→ 400 {"error":"name: Required"}
```

و `move()` این شکست را **کاملاً می‌بلعید** (`if (r.ok) load()` بدون هیچ
`else`). پس دو فاز تمام، تخته هرگز ذخیره نمی‌کرد و باگ شبیه یک مشکل درگ
front-end به‌نظر می‌رسید.

این توضیح می‌دهد چرا کاربر گفت «دوباره کار نمی‌کند» با وجود دو رفع قبلی:
- ۲۶.۲۹ مکانیک درگ را درست کرد — واقعی بود، ریشه نبود
- ۲۶.۳۳ کلیکِ پس از `pointerup` را درست کرد — واقعی بود، ریشه نبود
- **ریشه این بود که نوشتن اصلاً هرگز موفق نمی‌شد** — روی هر دستگاهی، هم با
  درگ و هم با انتخابگر مرحله (چون هر دو `move()` را صدا می‌زنند)

### رفع

1. `updateSchema = upsertSchema.partial().extend({ id })` — به‌روزرسانی نباید
   فیلدی را که تغییر نمی‌دهد اجبار کند. خودِ handler از قبل بدنه را روی رکورد
   موجود merge می‌کرد؛ فقط schema اشتباه بود.
2. `move()` حالا خطای سرور را نمایش می‌دهد (قرارداد ۲۶.۲۹).

### اثبات

```
PUT {"id":27,"status":"qualified"}  → 200 {"ok":true,"score":45}
psql: 27 | E2E Kanban Lead | qualified          ← واقعاً ذخیره شد
POST {"source":"other"}             → 400 {"error":"name: Required"}   ← قرارداد ساخت دست‌نخورده
```

E2E کانبان که در ۲۶.۳۳ `fixme` بود، **حالا کامل سبز است: ۳/۳** — و همان تستِ
`fixme` بود که این ریشه را آشکار کرد، چون علیه سرور assert می‌کرد نه علیه DOM.

### شکار هم‌خانواده — یافته، رفع‌نشده (آگاهانه)

همان الگو (schema ساخت برای به‌روزرسانی) در سه روت دیگر هست و **تجربی تأیید شد**:

```
PUT /api/admin/flags       {id,enabled} → 400 {"error":"key: Required"}
PUT /api/admin/workflows   {id,status}  → 400 {"error":"key: Required"}
PUT /api/admin/erp/assets  {id,status}  → 400 {"error":"name: Required"}
```

**عمداً رفع نشد.** برخلاف CRM، این سه handler مقادیر را مستقیم از `d.*` بدون
fallback به رکورد موجود می‌نویسند؛ partial کردن schema بدون افزودن merge
باعث می‌شود فیلدها **NULL شوند** — روی دادهٔ دارایی و مالی. این نیاز به یک
پاس دقیق per-field دارد، نه یک تغییر عجولانه در انتهای فاز. ثبت شد با شواهد.

فعلاً بی‌خطر است چون هیچ UI فعلی به این سه روت درخواست partial نمی‌فرستد.
