## 2. 🔴 هیچ عدد قانونی در کد نیست

`src/lib/hr/payroll.ts` هیچ نرخ، پله یا مبلغ قانونی ندارد. تنها ثابت‌های عددی
موتور، ثابت‌های حسابی‌اند (۱۰۰ برای درصد، ۶۰ برای دقیقه). همه‌چیز آرگومان است:

```
calculateSlip({ employee, employment, worked, loans,
                params, brackets, earningTypes, manual })
```

پارامترهای ۱۴۰۵ فقط **seed اولیه** هستند و seed غیرمخرب است: اگر کاربر مقداری
را عوض کرده باشد، اجرای دوبارهٔ مهاجرت بازنویسی‌اش نمی‌کند.

## 3. 🔴 چرا نسخه‌بندی درون سال، نه فقط سال

قانون ممکن است وسط سال با بخشنامه عوض شود. اگر مجموعه‌قوانین فقط با سال
شناخته می‌شد، تغییر تیرماه، فیش‌های فروردین تا خرداد را هم بازنویسی می‌کرد —
یعنی رقمی که به سازمان امور مالیاتی گزارش شده و در دفتر کل نشسته، بی‌صدا عوض
می‌شد.

اثبات زنده:

```
✅ 🔴 a ruleset that has issued payslips is frozen against editing
✅ a mid-year version can be created — {"ok":true,"id":2}
✅ 🔴 a bracket table with a DIFFERENT number of bands is accepted
✅ a statutory rate can be edited on the new version
✅ 🔴 the ISSUED payslip is unchanged by the new rules — gross — 390251120 → 390251120
✅ 🔴 the ISSUED payslip is unchanged by the new rules — tax — 0 → 0
✅ 🔴 it still names the version it was computed with
✅ a month after the change resolves to the new version — v2
```

## 4. 🔴 پلکان: تعداد پله آزاد است

جدول پلکان **ردیف** است نه ستون ثابت. اثبات: در همان اجرای زنده، جدول ۶ پله‌ای
با یک جدول **۴ پله‌ای** جایگزین شد و محاسبه بدون هیچ تغییر کدی دنبالش رفت. در
تست واحد هم یک جدول **۷ پله‌ای** آزموده شده است.

ذخیره‌سازی، جدول را **به‌عنوان یک مجموعه** اعتبارسنجی می‌کند — شکاف، همپوشانی و
پلهٔ آخرِ بسته رد می‌شوند:

```
✅ a table with a GAP is refused — بین این پله و پلهٔ قبلی شکاف وجود دارد
```

این‌ها هیچ‌کدام موقع محاسبه خطا نمی‌دهند؛ فقط **بی‌صدا مالیات را اشتباه حساب
می‌کنند**. پس جلوی نوشتن گرفته می‌شوند، نه بعد از آن.

**معافیت دوبار اعمال نمی‌شود.** جدول پلکان معافیت را به‌عنوان پلهٔ اول با نرخ
صفر در خود دارد؛ اگر پارامتر `monthly_exemption` هم کسر می‌شد، ۴۰۰ میلیون ریال
دوبار معاف می‌شد — خطایی کاملاً خاموش و ده‌ها میلیونی در هر فیش. پارامتر فقط
**نمایشی** است و اگر با جدول هم‌خوان نباشد، UI هشدار قرمز می‌دهد
(`exemptionMismatch`).

## 5. 🔴 مشمولیت، مقررات است نه کد

اینکه بن کارگری مشمول بیمه هست یا نه، **تغییر می‌کند**. پس هر قلم حقوقی پرچم‌های
خودش را دارد: مشمول بیمه (بله/خیر/تا سقف)، مشمول مالیات، مستمر/غیرمستمر، و
اینکه وارد مبنای عیدی و سنوات می‌شود یا نه.

اثبات که این واقعاً داده است، نه تزئین:

```
✅ 🔴 items flagged exempt from insurance stay out of the base — 352000000
✅ 🔴 a brand-new earning type can be defined from data alone
✅ 🔴 the new earning type appears on it (hardship, 40,000,000)
```

و در تست واحد: برگرداندن **یک پرچم** روی «بن کارگری» مبنای بیمه را دقیقاً
۲۲٬۰۰۰٬۰۰۰ ریال کم می‌کند — بدون یک خط تغییر کد.

مبنای عیدی و سنوات همین‌جا محاسبه می‌شوند (`eidBase`/`severanceBase`) تا
۲۸.۳-ب بدون تغییر مدل ساخته شود.

## 7. 🔴 دورهٔ قفل‌شده و فیش اصلاحی

فیش نه ویرایش می‌شود نه حذف. اصلاح، سه سند می‌سازد:

```
✅ 🔴 the ORIGINAL payslip is NOT deleted or edited — 390251120
✅ 🔴 the original is marked reversed and linked to its reversal
✅ 🔴 a reversing slip cancels it exactly — -390251120 vs -390251120
✅ 🔴 original + reversal net to zero, leaving only the correction
✅ a slip cannot be corrected twice
```

همان انضباط سند معکوس دفتر کل (۲۶.۲۶b BUG-020): اصلی `posted` می‌ماند، برگشتی
خنثی می‌کند، اصلاحی جایگزین می‌شود — و تاریخچه هنوز خودش را توضیح می‌دهد.

## 8. نگاشت دفتر کل + باگی که اجرای زنده پیدا کرد

**سند دوره:**

| طرف | حساب | مبلغ |
|---|---|---|
| بدهکار | ۶۱۰۰ هزینهٔ حقوق و دستمزد | جمع مزایا |
| بدهکار | ۶۱۱۰ هزینهٔ بیمهٔ سهم کارفرما | سهم کارفرما + بیکاری |
| بستانکار | ۲۳۱۰ بیمه پرداختنی | سهم کارمند + سهم کارفرما |
| بستانکار | ۲۳۲۰ مالیات حقوق پرداختنی | مالیات |
| بستانکار | ۱۱۶۰ وام کارکنان | اقساط |
| بستانکار | ۲۳۰۰ حقوق پرداختنی | خالص + سایر کسورات |

نگاشت از `erp_settings` با کلیدهای `gl_map_payroll_*` خوانده می‌شود.

**قسط وام، حساب دریافتنی را بستانکار می‌کند، نه درآمد را.** اگر این پا اشتباه
می‌شد، کل دفتر وام به‌عنوان درآمد شناسایی می‌شد.

### 🔴 باگی که فقط اجرای زنده نشانش داد

سند تراز نشد — **۱۲۰ ریال** کسری در سمت بستانکار.

علت: سیاست **گرد کردن** خالص پرداختی. خالص از ۳۶۵٬۶۱۱٬۱۲۰ به ۳۶۵٬۶۱۱٬۰۰۰ گرد
شد، ولی جمع مزایا کامل هزینه شده بود — پس ۱۲۰ ریال بخار شد. فیش هم دیگر جمع
نمی‌خورد: مزایا منهای کسورات با خالص برابر نبود.

اصلاح: تفاوت گرد کردن یک **سطر صریح** روی فیش شد («تعدیل گرد کردن»). این مبلغ
هنوز به کارمند بدهکاریم — درآمد شرکت نیست — پس داخل «حقوق پرداختنی» می‌ماند و
سند تراز می‌شود. سه تست واحد این کلاس را قفل کردند.

تست واحد به‌تنهایی این را نمی‌گرفت، چون داده‌های تست خودم گرد نمی‌شدند. فقط
اجرای واقعی با پارامترهای واقعی نشانش داد.

### مانده‌های اثبات‌شده (نه فقط «تراز است»)

طبق قاعدهٔ ۲۶.۲۶c بند ۲، «تراز متوازن» ادعای ضعیفی است. مانده‌های واقعی:

```
✅ 🔴 payroll expense is debited with the gross
✅ 🔴 salaries payable is credited with the net owed to employees
✅ 🔴 insurance payable carries BOTH shares
✅ 🔴 tax payable carries the withheld tax
✅ the trial balance still ties out
✅ 🔴 posting twice does NOT double the payroll expense
```

## 9. ⛔ بند ۸ — آزمون تطبیق انجام نشده

spec می‌گوید اگر فیش مرجع در دسترس نبود، فاز با برچسب صریح «منتظر آزمون تطبیق»
بسته شود و یک محاسبهٔ کامل در گزارش بیاید. §6 همان است — هفت سناریو، همه با
تابع تولید.

**آنچه از شما لازم است:** برای هر سناریو (یا سناریوهای واقعی خودتان) یک فیش
مرجع یا محاسبهٔ دستی حسابدار، تا جدول مقایسهٔ جزء‌به‌جزء پر شود:

| جزء | مقدار مرجع | مقدار سیستم | اختلاف |
|---|---|---|---|
| … | (منتظر) | §6 | — |

تا آن زمان، ادعای این گزارش این است: **فرمول‌ها همان‌اند که spec توصیف کرده و
پارامترها داده‌اند** — نه اینکه ارقام با فیش واقعی سازمان شما تطبیق دارند.

دو نکته که مخصوصاً ارزش بررسی دارند:
- **ساعت کاری روزانه ۷.۳۳** به‌عنوان مبنای مزد ساعتی seed شده (۲۲۰ ساعت در ماه).
  اگر سیاست شرکت شما فرق دارد، پارامتر `daily_work_hours` را عوض کنید.
- **ضریب شب‌کاری ۱.۷۵ و نوبت‌کاری ۱.۱۵** مقادیر متعارف‌اند نه نص قانون؛ اینها
  در گروه «سیاست شرکت» هستند و باید با قرارداد شما تطبیق داده شوند.
